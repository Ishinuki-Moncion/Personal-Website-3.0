# Rain + liquid simulation — 2026 technique options (research, no build)

**Date:** 2026-07-10. **Track:** owner ask — "the rain could be improved further… light simulation or liquid simulations with the rain."
**Scope:** practical technique space for elevating rain in THIS scene — Three.js **r158 WebGL** (pinned, import-map ESM, no bundler), two-composer selective-bloom postFX, GitHub Pages static hosting, LITE tier for phones, warm-LCP ≈ 257 ms budget.
**Method:** read the as-built rain system first (`js/background.js` at v3-build HEAD), extend the accepted `2026-07-03-rain-elevation-brief.md` levers rather than restart, then survey 2026 state-of-the-art with sources. Every option states: GPU cost class, mobile/LITE viability, **what existing layer it retires** (owner law: don't add a layer without retiring one), and **luminance-law impact** (rain is motivated light; nothing may raise the deep-black floor — p50 luminance floors 8/7/9 are law, `2026-07-08-v32-law-addendum.md` §8b).

Cost classes used throughout: **small** = no new render targets, sub-0.3 ms class, LITE-safe or cleanly LITE-skipped · **medium** = one new cheap pass/texture or measurable canvas work, needs a luminance gate · **large** = new full-screen GPU pass(es) or render-target machinery, desktop-only.

## 1. As-built inventory (what exists to extend or retire)

All line refs `js/background.js` at v3-build HEAD (working tree of 52b167a).

1. **Depth rain — 3 `THREE.Points` planes** (`makeDepthRain()` :499–534). High tier 70+150+250 = **470 drops**, LITE 80+130 = **210**, camera-space (group parented to camera), `PointsMaterial` + `makeStreakTexture()` canvas sprite (:1030–1046), additive, `sizeAttenuation`. Per-frame CPU loop moves every drop and recycles at the bottom (:1346–1358). Terminal opacity per **plane**: `baseOp × vis × beat × motivation` (:1369).
2. **Motivated light wells (v3.2l, brief Lever A as shipped)** — ≤3 screen-projected emitter wells (Tokyo halo / focused place / live lightning), evaluated **per plane, never per drop** (:1296–1338, :1360–1368). `MOTIV_FLOOR 0.16`, `MOTIV_CAP 0.80`; LITE skips all projection math (flat veil 0.55).
3. **Rain-on-glass droplet overlay — 2D canvas** (`droplets` IIFE :646–753). Cap 24 (LITE 12), ~30 fps via frame-skip, beads condense→swell→run, trails via `destination-out` decay, each bead ≥3 px **samples the live rendered frame** (`renderer.domElement` drawImage), inverted 180°, `ctx.filter saturate(0.5) brightness(0.9)`, alpha capped 0.22 (brief Lever D, shipped). Runs **after** render/composer, so it reads the graded frame (:2184). Drops that finish just `splice` — **nothing lands**.
4. **Sheet lightning** — one 64 px radial-gradient sprite behind the globe (:1118–1153), decaying flicker env returned as `flash`, lifts all rain via `beat` and feeds well 3. Falloff is still the roughly-linear gradient the brief's Lever F wanted reshaped.
5. **Wind/shear** — `wind = 0.10 ± 0.05 sin + scroll shear clamp ±0.6` (:1340) advects drop x, but the streak **texture angle is baked** (~10° slant, :1033–1034). Under full shear the velocity vector leans >30° while the sprite stays at 10° — drops visibly slide sideways without leaning. This is the main "cheapness tell" in the current rain.
6. **Bloom integration constraint** — depth-rain is deliberately **excluded** from the bloom emitter set (:1780–1781); untagged objects are swapped to type-correct invisible dark materials during the bloom pass (:1919–1935). Any new rain material must have a type-correct dark swap or it will stamp holes in the bloom buffer (the v3.1g lesson).
7. **Measured envelope** — hero depth-rain rest contribution to frame mean is **below measurement resolution** (interleaved A/B median Δ −0.01, addendum "Hero rain isolation A/B"). That is the bar: elevations may redistribute rain light but must keep net contribution ≈ 0 at rest.

Brief levers already shipped: A (per-plane wells), D (desat lens). Never built: **B (wet-ground reflections), C (splash landings), E (far-plane haze — partially: only layer-0 tints), F (directional lightning), G (mist)**.

## 2. Technique survey (2026 state of the art, sourced)

### 2a. GPU particle rain — velocity-stretched quads/lines
The consensus quality technique is **instanced quads stretched along the velocity vector in the vertex shader** (streak length ∝ speed, streak angle = actual fall+wind vector), replacing point sprites whose texture angle can't follow wind. Modern write-ups of Three.js particle craft recommend instanced quads over `THREE.Points` precisely for "arbitrary shapes, ribbons, trails" and to escape `gl_PointSize` limits ([tigerabrodi — particle systems in three.js](https://tigerabrodi.blog/particle-systems-in-games-with-threejs-and-tricks-to-make-them-look-good)). Cheap-rain practice keeps drop motion **on the GPU** — recycle by wrapping y in the shader from a time uniform instead of a CPU per-drop loop ([Peter Adams, "Cheap, Beautiful Rain in Three.js", Apr 2026](https://medium.com/antaeus-ar/cheap-beautiful-rain-in-three-js-9b62bbeabbf3): Points + blurred head/tail texture, drops recycled "vertically so they appear to fall forever without respawning on the CPU", targets "desktop computers, mobile phones, VR headsets"). The official rain showcase, [three.js `webgpu_compute_particles_rain`](https://threejs.org/examples/webgpu_compute_particles_rain.html), runs 25k–50k instanced drops with compute-shader physics and floor-collision via a top-down height render target — **WebGPU/TSL only, not reachable from the r158 WebGL pin** (renderer migration = rebuild of the two-composer bloom dark-swap; rejected below with the fluid sims).

**Soft particles / depth-fade** (fade drop alpha near intersecting geometry, via a `DepthTexture` prepass — [keaukraine, "Implementing soft particles in WebGL"](https://dev.to/keaukraine/implementing-soft-particles-in-webgl-and-opengl-es-3l6e), [three.js forum on soft-particle cost](https://discourse.threejs.org/t/soft-particles-rendering-performance/27610)): requires an extra depth render target and a depth-reading material. **Not applicable here** — this scene has *no opaque occluders by design* (every emitter is additive, `depthWrite:false`; the dark-swap pattern depends on that). There is nothing for rain to intersect; a depth prepass would be pure cost with zero visible payoff. Rejected.

### 2b. Screen-space droplet/rivulet glass
Two canonical lineages:

- **Lucas Bebber / Codrops "Rain & Water Effect Experiments"** ([article](https://tympanus.net/codrops/2015/11/04/rain-water-effect-experiments/), [repo](https://github.com/codrops/RainEffect)) — drop *simulation* on canvas 2D (two canvases: static small drops accumulate; large moving drops erase small ones beneath via `destination-out` = free trails + merge illusion), then one WebGL pass reads the drop canvas as a **normal-encoded texture** (G channel → x offset, R channel → y offset) to refract a background texture. Merging, trails, and the inverted-image refraction all come from this pattern.
- **SardineFish `raindrop-fx`** ([repo](https://github.com/SardineFish/raindrop-fx), MIT) — full WebGL2 rewrite: physics-lite raindrop dynamics (gravity, collision-merge with configurable collider size, evaporation, trail-drop spawning), refraction against **background blur mipmaps**. Measured by the author: **~2–3 ms/frame @600 drops, 1080p desktop Chrome; ~6.5 ms @2000 drops on a Mi 10 (Android)**; recommends ≤2000 spawn. Caveat for us: it takes a *background image/canvas*, not a live scene texture — feeding it the rendered frame means a per-frame texture re-upload of the whole canvas, which is the expensive path. A bespoke pass sampling the composer's output target directly (grabpass-style) avoids that upload entirely.
- Rivulet motion detail (zigzag, hang-and-burst runs, flow-map distortion) is documented in [Toadstorm's rainy-glass shader breakdown](https://www.toadstorm.com/blog/?p=742) and the shader-side small-drop fields in [greentec's Shadertoy rain-drops walkthrough](https://greentec.github.io/rain-drops-en/).

**Comparison against the existing 2D overlay:** the site's canvas overlay already does live-frame refraction (drawImage from `renderer.domElement` is a GPU-composited canvas-to-canvas blit in Chromium — no readback, no upload) at 24 beads/30 fps for near-zero cost. What it *lacks* vs the GPU lineage: bead–bead **merging**, spawned **trail droplets** along a run, per-pixel **normal-based refraction** (its inversion is a blunt rotate), and scale (hundreds of drops). The first two are O(n²) at n=24 (276 pair checks @30 fps — free) and fit the current code; the last two need the GPU pass.

### 2c. Puddle / ripple simulation
The production-standard technique is **procedural ripple normal maps**, not fluid sim: a tiling texture where each cell stores ring attenuation (R), perturbation direction (GB), and a per-cell random time offset (A); animate with `frac(time + A)` so rings never sync; **pack 4 layers in RGBA and enable one layer per quarter of rain intensity**. Cost measured by Lagarde at **~0.14–0.15 ms to generate a 256×256 ripple normal texture on PS3/Xbox-360-class GPUs** — i.e. effectively free on 2026 hardware ([Sébastien Lagarde, "Water drop 2b — dynamic rain and its effects"](https://seblagarde.wordpress.com/2013/01/03/water-drop-2b-dynamic-rain-and-its-effects/); splash sprites and surface wetness in [2a](https://seblagarde.wordpress.com/2012/12/27/water-drop-2a-dynamic-rain-and-its-effects/)). The modern indie version bakes the ripple math to a **flipbook normal texture** sampled once ([Cyanilux, "Rain Effects Breakdown"](https://www.cyanilux.com/tutorials/rain-effects-breakdown/)). Rain-on-surface droplet fields (SDF/Voronoi dots with time-fract fade, sliding streaks masked by surface normal) are the same family.
**Blocker here:** every one of these assumes a **lit ground/receiving surface**. This scene has none — the globe floats over a synthwave grid on a #05060a void. A literal puddle plane = a brand-new lit layer (violates retire-one, raises the floor). The native translation is to spend ripples on surfaces that already exist: the **grid** (vertex/opacity ring where a drop "lands") or the **wet-ground reflection band** of brief Lever B (ripple-jitter the smear columns). See options R4/R5.

### 2d. True fluid simulation — feasibility with numbers
- **FLIP/PIC (David Li "Fluid Particles")** — the reference browser implementation ([david.li/fluid](http://david.li/fluid), [repo](https://github.com/dli/fluid), [Google Experiments page](https://experiments.withgoogle.com/fluid-particles)): real-time at **~100k particles on a desktop iGPU**, consuming essentially the whole frame budget for the sim alone. A FLIP step is a multi-pass pipeline (particle→grid transfer, pressure projection = dozens of Jacobi/relaxation full-grid passes, grid→particle) — a **~100× cost-class jump** over the current rain system, whose measured rest contribution is below luminance/perf resolution. Mobile: not viable at any scale that would read as rain.
- **SPH** — neighborhood search is the WebGL bottleneck (no compute shaders on the r158 WebGL path); browser SPH/PIC-FLIP hybrids are showcased under **WebGPU** for exactly that reason ([jeantimex WebGPU SPH/FLIP](https://github.com/jeantimex/fluid), [Codrops "WebGPU Fluid Simulations", Feb 2025](https://tympanus.net/codrops/2025/02/26/webgpu-fluid-simulations-high-performance-real-time-rendering/)).
- **Eulerian stable fluids ([PavelDoGreat WebGL-Fluid-Simulation](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation))** — runs on phones, but only by being a 2D dye/smoke solver at reduced sim resolution: ~30+ full-screen sim passes per frame (advect, curl, vorticity, divergence, ~20 pressure Jacobi iterations, gradient subtract). Several ms/frame on mobile, and the output aesthetic is *smoke*, not rain — wrong instrument for streak rain and a direct competitor to the postFX budget.
- **WebGPU compute rain** (three.js official example above): the genuinely modern answer (25k drops + collision ripples), but requires `WebGPURenderer` + TSL node materials. On this project that is a renderer migration off the r158 pin, a rewrite of the alpha-preserving two-composer bloom, and a new set of Safari/Firefox fallback tiers. **Rejected for this site: the cost is an engine rebuild, not an effect.**

**Verdict: true fluid sim is confirmed too heavy — by two orders of magnitude on the sim itself, plus (for the WebGPU variants) an engine migration.** Say it once, close the door: the *look* of liquid (merge, rivulets, ripples, splashes) is achievable with the parametric techniques above at small/medium cost; the *simulation* of liquid is not budget-compatible.

## 3. Options

### R1 — Velocity-stretched instanced streak quads + per-drop light wells *(the core upgrade)*
**What:** Replace the 3 `THREE.Points` planes with one `InstancedBufferGeometry` quad batch (470 instances high / 210 LITE; per-instance attrs: seed xyz, speed, layer id). Vertex shader: stretch the quad along the **actual velocity vector** (fall speed + wind + scroll shear uniform) so fast drops draw longer and every drop *leans with the wind* — fixing the baked-10°-sprite-vs-30°-drift mismatch (inventory §1.5). Move the recycle math into the shader (`y = mod(seedY − speed·t, 2·halfH)` per the cheap-rain pattern) — deletes the per-frame CPU loop over 470 drops (:1346–1358). Evaluate the **existing 3 motivation wells per drop in the vertex shader** (wells as 3 vec4 uniforms: screen xy, depth z, strength) instead of per plane — brief Lever A finally lands at full strength: rain brightens *inside* a light pool and dies between pools, instead of whole planes brightening on average. Lever F's directional lightning becomes free: well 3 already carries the strike position; per-drop falloff makes near-strike drops over-brighten while the far field barely reacts.
**GPU cost class: small.** Same fill as today (points already rasterize as quads), 1 draw call instead of 3, ~1.9k vertices, 3 `exp()` per vertex. CPU drops (loop deleted). No new render targets.
**Mobile/LITE:** yes — instancing is core WebGL2; LITE keeps the flat-veil uniform (wells skipped by `#define`/uniform zero) and 210 instances.
**Retires:** the three `Points` layers, `makeStreakTexture()` sprites, and the CPU advection loop — a strict 1:1 replacement, not an addition. Scene object count goes *down* (3 → 1).
**Luminance impact: net-negative or neutral by construction.** Terminal opacity formula (`baseOp × vis × beat × motivation`, MOTIV_FLOOR/CAP) carries over verbatim; per-drop wells *concentrate* the same light budget into smaller pools (drops outside wells fall toward the floor that per-plane averaging used to hand them). Keep the interleaved A/B gate: median Δ vs current build must stay ≤ 0.
**Integration risks:** (a) bloom dark-swap needs a type-correct invisible material for the new instanced mesh (`MeshBasicMaterial opacity:0` works for InstancedMesh in r158 — same pattern as :1927); rain stays *excluded* from the bloom set per design §2c. (b) One-signal law untouched — rain is weather, not a motion signal, and the beat/lock coupling is unchanged.

### R2 — Droplet-glass v2 on the existing 2D canvas: merge, trail beads, emitter bokeh
**What:** Elevate the existing `droplets` IIFE in place (the Lever-D pattern — elevation, not new mechanism). Three sub-moves, all from the Bebber/raindrop-fx playbook: (1) **merge** — O(n²) pair check at n≤24, overlapping beads absorb (radius²-conserving), the survivor jitters and briefly accelerates — the single most "liquid" read at this scale; (2) **trail beads** — a running drop spawns 1–3 tiny static beads along its wobble path (they already fade via the `destination-out` decay), selling the hang-and-burst rivulet rhythm; (3) **emitter bokeh** (brief ref rain/017) — behind beads only, 2–4 soft colored discs at the projected well positions (Tokyo halo / callout), drawn dim under the bead field so distant emitters read as out-of-focus city lights through wet glass.
**GPU cost class: small.** All canvas-2D at the existing 30 fps half-rate; ~300 pair checks/frame; bokeh = 2–4 radial gradients.
**Mobile/LITE:** merge + trails yes (n=12); bokeh non-LITE only (needs the wells, which LITE skips).
**Retires:** nothing — and adds no layer; it is in-place elevation of an existing layer (same category as shipped Lever D). Bead cap unchanged, so peak glass coverage cannot rise.
**Luminance impact: ≈ 0.** Merging *reduces* live bead count; trail beads are smaller than the parent; bokeh discs must sit under the existing 0.22-alpha glint law and inside well positions (motivated). Gate: bead-area cap asserted in code; hero A/B unchanged.

### R3 — GPU rivulet-glass pass (grabpass refraction) — the "liquid headline," desktop-only
**What:** Replace the 2D canvas overlay with a bespoke screen-space pass in the existing composer chain: a **drop-state texture** (e.g. 64×64 RGBA via `GPUComputationRenderer` ping-pong — [docs](https://threejs.org/docs/pages/GPUComputationRenderer.html), same machinery as the official [webgl_gpgpu_water](https://github.com/mrdoob/three.js/blob/dev/examples/webgl_gpgpu_water.html) example and the [Codrops GPGPU particle tutorial](https://tympanus.net/codrops/2024/12/19/crafting-a-dreamy-particle-effect-with-three-js-and-gpgpu/)) holding per-drop position/velocity/size with gravity, hang-and-burst runs, evaporation, and collision-merge in the sim shader (raindrop-fx's model); then a full-screen pass that splats drops as SDF metaballs (smooth-min = real merge menisci), derives normals from the SDF, and **refracts the already-rendered frame** by sampling the previous pass's target with a normal-driven UV offset — a true grabpass, zero texture uploads (unlike embedding raindrop-fx, whose image-background API would force per-frame canvas re-upload). Slot: after `gradePass`, before `caPass`, so drops refract the graded world and still receive the lens fringe.
**GPU cost class: large.** Two tiny sim passes (64×64 — negligible) + **one added full-screen pass** on top of the existing ~10-pass chain (RenderPass ×2, bloom mips, mix, Output, grade, CA) ≈ +8–12% postFX fill on desktop. Reference numbers: raindrop-fx measures 2–3 ms @600 drops/1080p desktop *with* mip-blur; ours is cheaper (single-tap refraction, no blur chain, ≤200 drops fits the site's restraint).
**Mobile/LITE: no.** Bloom/composer is already high-tier-only; this pass rides the same gate. LITE keeps… nothing extra — see retirement.
**Retires (the law pairing):** the **entire 2D droplet canvas** — DOM element `.scene-droplets`, its CSS, the IIFE, and its per-frame drawImage work — on the high tier. Honest wrinkle: LITE currently *has* canvas droplets (cap 12). Either LITE keeps the old canvas (two implementations alive — maintenance smell, but each tier runs exactly one) or LITE loses glass drops entirely (cleaner; LITE never had refraction anyway, :652). Recommend the latter and record it.
**Luminance impact: neutral if clamped.** Refraction redistributes existing frame light; the 0.22-alpha glint law becomes a shader clamp on the refracted sample's added luma; SDF highlights must stay under the same cap. Risk to gate: metaball fields tempt toward *more coverage* — pin a max total covered-area uniform and A/B the hero median. Also: sampling after grade means drops show graded (already floor-crushed) light — correct by design.
**When it's worth it:** only if the owner wants a visible "liquid simulation" signature moment. R2 delivers ~70% of the read at ~5% of the cost. This is the splurge tier, and it's the only proposal that genuinely earns the word "simulation."

### R4 — Wet-ground reflection band + splash landings (brief Levers B + C, with a retirement pairing)
**What:** The two never-built levers the brief calls the wetness sell. (1) **Reflection band:** bottom ~12% of frame on the existing droplet canvas — for each active well/emitter (Tokyo halo, callout, live lightning), draw a vertically-flipped, vertically-smeared, dimmed strip of the rendered frame (one clipped canvas-to-canvas drawImage per emitter, ≤3/frame, gradient-masked to black at the band's top edge), with slow per-column sinusoidal jitter as the "water" (the 2D translation of Lagarde's ripple perturbation). (2) **Splash landings:** near-plane drops crossing the band's screen y (a one-line check in R1's shader → or CPU-side on recycle) spawn from a pool of ~8 expanding stroked ellipses + 2–3 rising micro-beads, 0.3 s life, **only inside a well's footprint** — rain lands where light is, per rain/025's three-part rule (source, shaft, landing). (3) **Retirement pairing (proposed):** delete the sheet-lightning **scene sprite** (:1118–1133) and re-home lightning as a directional top-band gradient flash on this same canvas — Lever F's exponential falloff shaped in 2D where gradients are free; `flash`/well-3 coupling unchanged. One scene object retired, no new DOM layer (the canvas already exists), and lightning finally gets its directional shape.
**GPU cost class: medium.** 1–3 clipped drawImage blits + ≤8 ellipse strokes at the canvas's existing 30 fps half-rate. No WebGL cost.
**Mobile/LITE:** band yes at reduced alpha (it's the cheapest wetness signal per pixel); splashes non-LITE (they key off wells).
**Retires:** sheet-lightning scene sprite (per pairing above). Net: −1 scene object, 0 new layers.
**Luminance impact: THE risk of this option — it adds light to a formerly-black band.** Mitigations that must be law: band strips only under *live* emitters scaled by well strength (mostly-black frame ⇒ mostly-black band); per-strip alpha cap tuned so the **hero mean interleaved A/B stays below resolution** (the same bar the current rain passes at Δ −0.01); band excluded from LITE luminance budget by the reduced alpha. Gate exactly like v3.2 practice: §8b median-of-5, isolate via an `evaluate_script` toggle. Secondary risk: owner de-clutter taste — this is the most *visible* addition in this doc; ship behind a flag and let the owner call it on the board.

### R5 — Grid-ripple landings (the puddle translation) *(optional taste spike)*
**What:** Classic puddle/ripple tech (§2c) has no receiving surface here, so translate it onto the surface that already exists: when a splash fires (R4) — or, standalone, on well-gated random drops — pulse a **single expanding ring of brightness/displacement in the synthwave grid material** at that grid location (one vec4 uniform: xz center, birth time, strength; ring math is the Lagarde/Cyanilux `frac`-ring, ~6 shader ops). One live ripple max, 0.5 s decay.
**GPU cost class: small.** Uniforms + a few fragment ops in an existing material; zero new objects.
**Mobile/LITE:** yes (it's cheaper than everything else here), though gate to non-LITE anyway for calm.
**Retires:** nothing — but adds nothing either; it modifies an existing layer's shader. If a pairing is demanded: it can *replace* R4's canvas splash ellipses (ripple-in-grid instead of ring-on-canvas) so landings live in the world, not on the glass.
**Luminance impact:** an event light (decays to zero, ≤1 live) — same class as the shipped haloPulse beats. **One-signal law risk:** a ripple during a section-lock/state-word beat is a second simultaneous signal — must be suppressed while `lockT` is active, exactly like other event lights. Flagged as speculative art direction: it makes the grid read as *water*, which may or may not be the owner's read of the synthwave floor.

### R6 — True fluid simulation (FLIP / SPH / stable fluids / WebGPU compute) — **REJECTED, with numbers**
Full analysis in §2d. Summary of record: David Li's WebGL FLIP needs a desktop iGPU's *entire* frame budget for ~100k particles (multi-pass pressure projection); WebGL SPH is bottlenecked on neighborhood search without compute shaders; mobile-capable stable fluids ([PavelDoGreat](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation)) is ~30+ full-screen passes/frame of *smoke* aesthetics — wrong instrument; and the genuinely modern path ([three.js WebGPU compute rain](https://threejs.org/examples/webgpu_compute_particles_rain.html), 25k–50k drops with collision ripples) requires migrating off the r158 WebGL pin and rebuilding the alpha-preserving two-composer bloom — an engine rebuild, not an effect. The current rain's measured rest cost is ~0; every fluid-sim path is a 10–100× cost-class jump for a look the parametric options above fake convincingly. **Do not build. Revisit only if the project ever migrates renderers for its own reasons.**

---

## 4. Recommendation

Sequence by value-per-cost, laws held by construction:

1. **R1 now** — it *retires* more than it adds, deletes CPU work, fixes the one visible cheapness tell (streaks that don't lean with the wind), and completes Lever A per-drop + Lever F directional lightning in the same shader. Gate: interleaved luminance A/B ≤ 0, harness pin for MOTIV_CAP carried into the shader uniform.
2. **R2 with it** — small, in-place, and "merge" is the word *liquid* at 24-bead scale.
3. **R4 next, behind a flag + §8b-style gate** — the brief says reflections are what make the world read wet; it carries the only real floor risk in this doc, so it ships only after the median-of-5 A/B and an owner board verdict. Take the lightning-sprite retirement pairing with it.
4. **R5 as a one-uniform spike** riding R4's splash events — cheap to try, easy to kill; suppress during lockT.
5. **R3 only on explicit owner appetite** for a headline liquid-glass signature (desktop). It is the sole true "simulation" candidate that fits the budget, and its retirement pairing (the whole 2D droplet canvas) is clean.
6. **R6 closed** — recorded with numbers so it never resurfaces as an additive temptation.
