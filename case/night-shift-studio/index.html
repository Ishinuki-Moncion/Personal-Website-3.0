Why build it

Ad production at volume has three kinds of work. Some of it is truly creative. Some is identical every time. And some looks identical until it fails without warning. That third kind is what costs evenings.

Night-Shift takes the day's order and runs the mechanical part overnight, with nobody watching. The next morning there is a board of checked directions and a report of what it could not confirm. A pipeline that hides its doubts is worse than no pipeline.

It starts from what already worked

Before it proposes anything, the pipeline looks back. At the start of every job it checks two sources. One is the team's record of past jobs, brand specifications and review decisions. The other is the team's Creative Gallery: an archive of every ad that shipped, with its results.

The gallery can be searched four ways: by brand history, by measured performance, by visual similarity and by meaning. The meaning search uses a multilingual AI model, so a Japanese brief can find an English campaign, and the reverse.

Every search returns its results in the same shape. So a new kind of search can plug in without changing anything that reads the results.

It never fakes an answer

If one of those searches is unavailable, the run stops and says so. It never swaps in the newest work without saying so. Someone who asked for the best performers could not tell they got the most recent ones. A silent fallback is a wrong answer that looks right.

A fixed set of test questions with known answers guards the search. If the answers drift, the build fails.

Two editions, one source

The pipeline has to run on two kinds of machine: one that can reach everything it depends on, and one that can reach nothing. The obvious fix is a second copy with those dependencies bundled in.

That fix had already failed three times. Two hand-maintained copies drifted apart every time. Examples: a stale list of skills, an old pinned dependency, and a fix that reached only one copy. Each failure was silent and found late.

So nobody edits the second edition by hand. A build script generates it from the first, and a check confirms that the two still match. The failure changed from "someone forgets" to "the check fails". One test exists only to stop stray files from slipping into the generated copy.

Built for nobody being there

Running unattended shapes the design. An AI that stops to ask permission at 2 a.m. has not run. It has waited. So setup grants the permissions the run needs in advance, and the run never meets a prompt it cannot answer.

Missing dependencies get the same care. If a required one is missing, the run stops and names it. If an optional one is missing, the run continues with less, and the report says so. Setup checks the machine first and reports "ready", "partly ready" or "needs attention", instead of claiming success and failing later.

Nothing publishes

The strongest rule is a negative one. No part of the system publishes to the ad platform, sends a message, or deletes anything it did not create. It reads, it produces, and it reports.

That rule outranks everything else: if something breaks it, fixing that comes first. Automation that runs while nobody watches earns trust by what it cannot touch. The simplest way to limit that is to never grant the ability in the first place.

What the tests check

The important tests catch output that is wrong in ways a person would miss. A build goes over its size limit. A file changes when it should pass through untouched. Files appear in the generated edition that were never in the source.

The documentation is tested too. Version numbers in the docs are checked against the things they describe. The problem this project kept hitting was an instruction that had stopped being true while the program still ran.

How it was built

Each stage started as a dated design record before any code existed. I kept the records as written instead of editing them to match what shipped. That includes an audit of finished work, and a fix plan written after the first full run met reality.

A document rewritten to agree with the present proves nothing. A dated record is valuable because it shows what was believed at the time.

Where it is now

In November 2026 the pipeline moved into the company's own GitHub organization as a team tool. It follows the rules in the production kit. Each pipeline release is paired with a kit release, so the two change together on purpose.
