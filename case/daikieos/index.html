The problem

A portfolio for a developer and photographer has two jobs that pull against each other. It must prove engineering skill. It must also load fast enough that nobody leaves first.

The site has no build step. The browser gets the same JavaScript modules that are in the repository, linked by an import map. There is no bundler and no framework. The only outside code is a copy of three.js kept in the repository.

The 3D scene is optional

The WebGL scene costs the most and matters the least. So it is an add-on, which web developers call progressive enhancement.

Navigation, language switching, the gallery, the photo viewer and the contact button all start before the scene and never depend on it.

Tests enforce this. The browser tests block single files one at a time: three.js, the scene, the scene's own error handler, and the decorative custom cursor. Each time, the page must still appear, scroll and respond to every essential action.

Measuring what a device can handle

The site picks render quality by measuring the device, never by what the device says it is. Browser names, graphics-chip names and memory hints are all ignored. They describe what a device claims, and the measurement shows what it can do right now.

A short WebGL2 test runs after the page first appears. It draws a workload like the real scene. Then it reads back one pixel, which makes it wait for the GPU to finish, so the timing measures real work.

The test pauses between rounds so the page never freezes. Afterwards it frees every buffer, texture and shader it made, whether it succeeded, failed or timed out.

Reduced-motion settings win over all of this. With reduced motion on, the test never runs.

A memory budget you can compute

Visual effects applied after rendering (postprocessing) are where a phone's GPU runs out of memory. So the site adds up the memory those effects need before it allocates anything.

It compares that total with a fixed budget. Over budget, the scene renders without the effects. It never allocates and hopes.

Resizing the window allocates memory too, because every effect buffer is rebuilt at the new size. So the budget is checked again on every resize, with the same fallback.

When the measurement is wrong

If the frame rate stays low, a watchdog lowers the quality once per visit. It removes the effects, caps the pixel density (the cap survives rotating the phone), switches to plain rendering, and never raises the quality again.

That needed cleanup the library skips. three.js leaves one internal bloom material out of its own cleanup method, and still does in r187. So the site frees it explicitly, then drops every reference so nothing stays in memory.

Looking the same in Chrome and Safari

The scene once looked right in Chrome and washed out in Safari. The cause was how the browser blends the canvas onto the page. The shaders were fine.

Browsers blend a canvas using premultiplied alpha. Safari's engine (WebKit) clamps each colour to its transparency value, while Chrome passes larger values through.

A scene of glowing, additive light often produces colour above its own transparency. So Safari on iPhone crushed every glow and every faint raindrop.

The fix was to clear the canvas at full opacity, in linear colour space. Then every pixel is valid, and both browsers show identical results.

Delivering fonts is its own job

The two Japanese fonts came from an outside font service, behind a stylesheet that blocked the page. An old note said trimming Japanese fonts to the needed characters was impractical.

Measuring proved the note wrong. The pages use fewer than 200 different Japanese characters, so each font shrinks to well under 60 KB, about 98% smaller.

The old setup caused a second problem. Japanese text first appeared in a system font, then jumped when the outside font arrived.

Hosting the trimmed fonts on the site fixed both problems. The type design stayed the same, and the last outside server left the page.

What I would do differently

Some checks in this codebase look for specific text in the source code. They stop someone from deleting a safety check by accident. But they fail on correct rewrites, and they look like behaviour tests when they are not. I would keep the two kinds of check apart.

The repeatable speed test blocked the outside font request so every run matched. That also removed the biggest real-world cost from the measurement. A test that leaves out the biggest real cost measures a site nobody gets. Both modes now run, and the realistic one has to pass.
